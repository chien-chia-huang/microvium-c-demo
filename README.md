# STM32L433RC + Microvium: button -> timed LED demo

A minimal example: press B1, the user LED lights up, and turns itself off
after a configurable number of seconds. All of the "how long to stay lit"
logic lives in JavaScript (`js/agent.mvm.js`), run by the
[Microvium](https://github.com/coder-mike/microvium) engine on the MCU. The C
firmware only ever touches raw GPIOs and a millisecond clock.

## Board

- **Board:** NUCLEO-L433RC-P (Nucleo-64-P, MB1319)
- **MCU:** STM32L433RCT6P (LQFP64 package, 256KB flash, 64KB SRAM)
- **B1 (user button):** PC13, active LOW (pressed = electrical low), external pull-up on the board.
- **LD4 (user LED):** PB13. Labelled LD4 on this board's silkscreen (LD3 is the separate power/overcurrent indicator).

See `Core/Inc/app_config.h` for the pin definitions.

## Toolchain

- `arm-none-eabi-gcc` 9.3.1 (`/opt/gcc-arm-none-eabi-9-2020-q2-update`)
- `STM32_Programmer_CLI` (STM32CubeProgrammer) -- used by `make flash`
- `st-flash` / `st-info` (stlink-tools, via Homebrew) -- alternative, `make flash-stlink`
- `openocd` (Homebrew) -- alternative, `make flash-openocd`
- Node.js + npm -- used to run the `microvium` CLI via `npx`

## Where the STM32 vendor files came from

Rather than re-download STM32CubeL4 from the internet, everything was
vendored from your existing local cache at
`~/STM32Cube/Repository/STM32Cube_FW_L4_V1.18.1` (installed by STM32CubeMX),
specifically:

| File(s) | Source within STM32Cube_FW_L4 |
|---|---|
| `Drivers/CMSIS/Include/*.h` | `Drivers/CMSIS/Include/` (ARM CMSIS core headers) |
| `Drivers/CMSIS/Device/ST/STM32L4xx/Include/*.h`, `Source/Templates/system_stm32l4xx.c` | same path in the package |
| `startup/startup_stm32l433xx.s` | `Drivers/CMSIS/Device/ST/STM32L4xx/Source/Templates/gcc/` |
| `linker/STM32L433RCTX_FLASH.ld` | `Projects/NUCLEO-L433RC-P/Templates/STM32CubeIDE/` (modified -- see below) |
| `Drivers/STM32L4xx_HAL_Driver/{Inc,Src}/*` | same path in the package (only the RCC/GPIO/CORTEX/PWR/FLASH modules -- see Makefile) |
| `Core/Src/{syscalls,sysmem}.c` | `Projects/NUCLEO-L433RC-P/Templates/STM32CubeIDE/Example/User/` (newlib syscall stubs, incl. `_sbrk` for `malloc`) |
| `Core/Src/main.c` clock config | `Projects/NUCLEO-L433RC-P/Templates/Src/main.c` (`SystemClock_Config`, 80MHz MSI+PLL) |
| `Core/Src/stm32l4xx_it.c`, `stm32l4xx_hal_msp.c` | same-named files in `Projects/NUCLEO-L433RC-P/Templates/` |

If you're setting this up on a machine that doesn't have STM32CubeMX
installed, get the same package from ST directly: search "STM32CubeL4" on
st.com (or `STMicroelectronics/STM32CubeL4` on GitHub) and pull the
equivalent files from the paths above.

**One deliberate edit:** `linker/STM32L433RCTX_FLASH.ld` had its
`(READONLY)` section qualifiers removed. STM32CubeIDE generates that syntax
assuming GCC 11+, but this machine's `arm-none-eabi-gcc` is 9.3.1, whose
linker rejects it ("non constant or forward reference address expression").
The linker script itself has a comment noting exactly this.

## Microvium integration

`third_party/microvium/microvium.c`/`.h` and `microvium_port_example.h` were
generated by `npx microvium --generate-lib` (vendored as plain files, not a
git submodule, per your request) and copied in as-is. Only
`microvium_port.h` was written by hand, starting from the generated example
-- see the comment block at the top of that file for exactly what was
changed (mainly: smaller heap/stack sizes sized for this MCU's 64KB SRAM,
and snapshot/debug capabilities turned off since we don't need them
on-device).

### C <-> JS contract

Host functions (C, called from JS via `vmImport`), see `Core/Src/mvm_host.c`:

| ID | Name | Signature | Notes |
|---|---|---|---|
| 1 | `readButton` | `() -> 0/1` | Debounced B1 state. Exposed for future on-demand polling; the main loop already hands `onTick()` a fresh reading each tick (see below), so it isn't called from the tick path itself. |
| 2 | `setLed` | `(state) -> undefined` | Raw LED GPIO write. |
| 3 | `getTime` | `() -> ms` | `HAL_GetTick()`, milliseconds since boot. |

Export (JS, called from C via `mvm_call`), see `js/agent.mvm.js`:

| ID | Name | Signature | Notes |
|---|---|---|---|
| 100 | `onTick` | `(nowMs, buttonState) -> actionCode` | Called every 10ms (`APP_TICK_INTERVAL_MS`). Returns `0`=no change, `1`=turn LED on, `2`=turn LED off. |

The "should the LED be on" state machine (latch press time, compare against
`LIGHT_DURATION_MS`) lives entirely in `onTick()` in JS -- C never computes
a duration, it just forwards raw readings and applies the returned action.

## File structure

```

Core/Src/             main.c (clock+GPIO init, boot self-test, main loop), mvm_host.c (VM glue + host fns + logging),
                      debug_uart.c (USART2 console + printf retarget),
                      stm32l4xx_it.c/hal_msp.c (vendored), syscalls.c/sysmem.c (newlib stubs)
Drivers/CMSIS/        ARM CMSIS core + ST device headers/system file (vendored)
Drivers/STM32L4xx_HAL_Driver/   HAL modules actually used: RCC, GPIO, CORTEX, PWR, FLASH, DMA (header dep. of UART only), UART
startup/              startup_stm32l433xx.s (reset handler + vector table)
linker/               STM32L433RCTX_FLASH.ld (256K flash / 64K RAM)
third_party/microvium/  microvium.c/.h (generated engine), microvium_port.h (customized)
js/agent.mvm.js       the JS state machine (edit this to change behaviour)
tools/gen_bytecode_header.sh   compiles agent.mvm.js -> build/agent_bytecode.h
build/                generated: .o/.elf/.bin/.hex/.map + agent_bytecode.h (gitignored)
Makefile, package.json  build entry points
Dockerfile, .dockerignore   generic Ubuntu 22.04 + arm-none-eabi-gcc build image
```

## Building

Either build locally (needs `arm-none-eabi-gcc` and Node/npm on your PATH):

```sh
npm install      # installs the `microvium` CLI locally (once)
make             # compiles agent.mvm.js -> build/agent_bytecode.h, then builds firmware
```

or build in Docker (needs nothing but Docker itself -- see "Docker build" below):

```sh
make docker-build
```

Expected output ends with a size summary, e.g.:

```
   text    data     bss     dec     hex filename
  43536     132    1756   45424    b170 build/firmware.elf
```

(The Docker build uses a newer `arm-none-eabi-gcc`, 10.3.1 vs. the host's
9.3.1, so its size numbers differ slightly -- e.g. `46640` bytes of `text`
instead of `43536`. Same source, same functionality either way.)

`text` (code + constants, goes in flash) must stay under 256K; `data+bss`
(static RAM) plus the VM heap/stack (see the sizing note in
`third_party/microvium/microvium_port.h`) plus the 1KB main stack must stay
under 64K. There's ample headroom for this demo (currently ~1.7KB of the
64KB SRAM budget).

Editing `js/agent.mvm.js` and re-running `make` (or `make docker-build`)
automatically recompiles the bytecode and relinks the firmware -- no manual
copy/paste step.

## Docker build

`Dockerfile` builds an Ubuntu 22.04 image with `arm-none-eabi-gcc` (plus
Node/npm, which *this* project's build additionally needs for the
`microvium` CLI -- see `tools/gen_bytecode_header.sh`). It's deliberately
generic: no project files are baked into the image, so the same image can
build any Cortex-M project, not just this one -- `arm-none-eabi-gcc` is a
bare-metal cross-compiler for the whole ARM architecture (Cortex-M0 through
M7/M33 and beyond), selected per-project via that project's own `-mcpu`
flag. What's specific to a given chip/board -- CMSIS headers, HAL/LL
drivers, the linker script, the startup file -- lives in each project's own
repo (as it does here, under `Drivers/`, `linker/`, `startup/`), not in the
image. So the same image works for a future Cortex-M0+ or Cortex-M33
project too, as long as that project brings its own vendor files and points
its Makefile at the right `-mcpu`.

```sh
make docker-image   # docker build -t arm-cortex-m-toolchain:22.04 .
make docker-build   # npm install && make, inside that image
make docker-shell    # interactive shell in the container, project mounted at /work
```

`node_modules` is kept in its own named Docker volume rather than the
project directory: `microvium` ships a native addon, and a copy built on
your host (e.g. macOS) can't load inside the Linux container, or vice
versa. This keeps the two completely separate so switching between a local
build and a Docker build never corrupts either one's `node_modules`.

Flashing is not done from inside the container -- it needs direct USB
access to the ST-LINK, which is awkward to pass through to a Linux
container from macOS/Windows Docker Desktop. Build with Docker, flash from
the host (below).

## Flashing

```sh
make flash            # via STM32_Programmer_CLI
```

`st-flash` and `openocd` both talk to the ST-LINK over raw libusb, which on
macOS hits a kernel-driver-detach permission error unless run as root (and
even then, may still fail depending on your macOS/security setup).
`STM32_Programmer_CLI` uses ST's own signed driver instead and sidesteps
this, which is why it's the default `flash` target. If you'd rather use one
of the others:

```sh
sudo env "PATH=$PATH" make flash-stlink   # via st-flash
make flash-openocd                         # via openocd
```

## Serial console

The firmware logs over the Nucleo's onboard ST-LINK Virtual COM Port (VCP)
on **USART2 = PA2 (TX) / PA3 (RX), 115200 8N1** -- this is the standard VCP
wiring on essentially every ST Nucleo-64 board. No extra wiring needed -- it
goes over the same USB cable already used for flashing/power.

**Connect:**

```sh
ls /dev/tty.usbmodem*        # find the port (macOS)
screen /dev/tty.usbmodemXXXX 115200
```

(Linux: `/dev/ttyACM0`. Windows: PuTTY/Tera Term, matching COM port, 115200
8N1. Exit `screen` with `Ctrl-A` then `k`, then `y`.)

**Example log**, boot followed by one press-and-release and one
press-and-hold-past-3-seconds:

```
=== STM32L433RC + Microvium button/LED demo booting ===
SystemCoreClock = 80000000 Hz
LED self-test: blinking LD4 (PB13) 3x...
LED self-test done.
mvm_host_init: restoring 166 bytes of bytecode...
mvm_host_init: VM ready, onTick exported OK.
Entering main loop (tick every 10ms)
[t=15462] PC13 electrical level -> HIGH
[t=15472] button released
[t=15622] PC13 electrical level -> LOW
[t=15632] button PRESSED
[t=15632] onTick -> ACTION_LED_ON, driving PB13 high
[t=16002] heartbeat: PC13=LOW button=1
[t=17002] heartbeat: PC13=LOW button=1
[t=18632] onTick -> ACTION_LED_OFF, driving PB13 low   <- exactly 3000ms after the press
[t=19002] heartbeat: PC13=LOW button=1                 <- still held, LED correctly stays off
[t=22312] PC13 electrical level -> HIGH
[t=22322] button released
```

Each line's meaning:

- `PC13 electrical level -> HIGH/LOW` -- the *raw, unfiltered* pin reading,
  logged before debounce or the active-low inversion. Useful for telling a
  genuine hardware/wiring problem apart from a software one.
- `button PRESSED` / `button released` -- the debounced, logical state.
- `heartbeat: PC13=... button=...` -- printed once a second so you can tell
  the main loop is alive even when nothing else is happening.
- `onTick -> ACTION_LED_ON/OFF` -- only printed when the JS state machine
  actually changes the LED (see `js/agent.mvm.js`).
- `mvm_restore failed: ...` / `mvm_resolveExports failed: ...` (not shown
  above; only appears on failure) -- printed with an `MVM_E_*` numeric code
  if the VM fails to start; cross-reference the `mvm_TeError` enum in
  `third_party/microvium/microvium.h` for what the number means.

If something isn't behaving as expected, reflash and watch which of these
lines you get and which you don't -- that narrows down whether the problem
is in the raw GPIO layer, the VM/bytecode, or the JS state machine.

## Testing the whole pipeline

1. `npm install && make && make flash`
2. Open the serial console (above) *before* or immediately after resetting
   the board, so you catch the boot banner.
3. Reset the board (press the black RESET button, or power-cycle).
4. Press and hold B1 -- LD4 (the user LED on PB13; don't confuse it with
   LD3, the power/overcurrent indicator) should turn on immediately (within
   one 10ms tick), and the console should print `button PRESSED` followed
   by `ACTION_LED_ON`.
5. Release B1 before 3 seconds are up -- the LED should stay on until
   3 seconds have elapsed since the press, then turn off automatically
   (console: `ACTION_LED_OFF`).
6. Press and hold B1 for *longer* than 3 seconds -- the LED should still
   turn off at the 3-second mark even while still held (confirms the timer,
   not "button still down", drives the light).
7. Press B1 again after the LED has gone off -- it should light again for
   another full 3 seconds (confirms the state machine resets cleanly).

To change the duration, edit `LIGHT_DURATION_MS` in `js/agent.mvm.js` and
re-run `make && make flash`.
